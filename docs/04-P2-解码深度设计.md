# P2 设计：解码深度专项（OSD / 精细对齐与逐符号 LLR / NEON / 常驻线程池）

> 前置：`docs/00-评估与总体设计.md`、`docs/02-测试报告.md`、`docs/03-P1-信号消除设计.md`
> 目标：在 P1 基础上继续逼近 JTDX，突破「≥82% 召回」并提高 SNR 显示精度；保持单时隙 P95 ≤ 500 ms。
> 许可证：仅参考 WSJT-X / JTDX 的**公开算法思路**，代码全部自研 C，保持整体 MIT（详见 §11）。

## 1. 背景与现状

P1 收官实测（Android x86_64 模拟器，4 线程，`test/` 60 文件 / 1298 条）：

| 配置 | 命中 | 召回率 | extra | P50 | P95 |
| --- | --- | --- | --- | --- | --- |
| P0 单遍（基准） | 942 | 72.6% | 2.0% | 9.5 ms | 12.5 ms |
| P1 默认（`--subtract --depth 3`） | 1048 | 80.7% | 2.9% | 203 ms | 260 ms |
| P1 调参（+`--time-osr 3 --candidates 280`） | 1063 | 81.9% | 3.3% | 230 ms | 280 ms |

剩余漏解约 235–250 条，集中在：

1. **极度拥挤频段**（单文件 30+ 同时信号，如 `test_21.wav`），相减后仍有多条相互重叠；
2. **弱信号**（参考 SNR ≤ −16 dB）约 60 条，接近噪声下限。

P1 已证明：**单纯加深遍数、降低 `min_sync_score` 均无进一步收益**（3 遍内收敛）。继续收敛必须做算法深度——即：

- **更准的软信息**（当前 LLR 受 2 符号窗 + 量化 + 无精细对齐拖累）；
- **更强的译码**（当前仅 BP，失败即丢弃，无 OSD 兜底）；
- **更高的性能余量**（为 OSD 与实时流式让出预算）。

## 2. 瓶颈诊断

| 环节 | 现状实现 | 主要问题 | P2 对策 |
| --- | --- | --- | --- |
| 候选对齐 | 复用瀑布量化格点，时间 80 ms、频率 3.125 Hz | 时间/频率残差直接损失相干增益 | 专项 A：精细对齐 |

## 3. 专项 A：候选精细对齐 + 逐符号频谱 LLR/SNR

### 3.1 动机

P1 的相减模块已经从「粗对齐 → 频偏估计 → 细对齐」中证明了精细对齐的价值（`docs/03` §10.1）。把这套能力**抽成公共模块**，既服务相减，也服务候选解码与 SNR，避免重复实现。

### 3.2 模块划分

```text
native/api/ft8_align.{h,c}   # 公共精细对齐：由粗 (dt, f) 估计精化 (dt*, f*)
native/api/ft8_spectrum.{h,c}# 逐符号频谱 LLR + SNR（依赖 ft8_align）
```

- `ft8_align_refine(samples, n, tones, f0_coarse, dt_coarse, &f_out, &dt_out)`
  与 `ft8_subtract.c` 现有三段式对齐同源（相关 / 频偏估计 / 参考调制 / 粗-细搜索）。
  **分两步落地**：先纯重构（抽取 `ft8_spectrum` 现有 `sp_align_refine` 为公共实现，结果逐位不变）；
  再评估是否让 `ft8_subtract` 采用同一策略（会改残差，需 A/B 全量对比，详见 §3.5.1）。
- `ft8_spectrum_llr(samples, n, tones, f0, dt, log174_out)`
  在精化位置逐符号做窄带 DFT/Goertzel，得到每符号 8 个音调功率；按 Gray 映射合成 174 个 LLR（详见 §3.5.2）。

### 3.3 软信息构造

对每个数据符号 `k`、每个音调 `j`：

- 在 1 个符号窗（960 样本 @12 kHz，或可选 1.5 符号窗）内对频率 `f0 + j·6.25 Hz` 做 Goertzel，得复幅度 `A_kj`；
- 噪声估计 `N_k` 取相邻保护音调（如 `j=−1`、`j=8`）功率均值，或全 8 音调扣除最强者的均值；
- 归一化幅度 `s_kj = |A_kj|² / N_k`；
- 按 Gray 映射（与 `kFT8_Gray_map` 一致）合成 3 bit 的 LLR：`llr_b = max_{j: bit_b=1} s_kj − max_{j: bit_b=0} s_kj`；
- 同步符号（Costas）不参与 LLR，仅可用于对齐（与现有实现一致）。

与现状的差异：**逐符号、含噪声归一、对齐到样本级**，而非「2 符号 Hann 窗量化幅度 + max-log」。

### 3.4 SNR 估计（频谱噪声底口径）

上报 SNR 采用 **WSJT-X 同源「频谱噪声底（spectrum baseline）」口径**：不再用「信号自身 8 音调中其余 7 个」的平均功率当噪声（旧「7 音调平均」口径），而是从**整时隙频谱中「没有信号」的区域**估计噪声底。

原因：7 音调口径把「其余 7 个音调」视为纯噪声，但同一时隙内邻近信号/强信号泄漏会污染这些音调，使强信号 SNR 被严重低估（实测一条 WSJT-X 报 +13 dB 的信号被压到 +0.6 dB，偏差 12 dB）。空闲频谱区域的噪声底不受该信号本身影响。

实现（`native/api/ft8_spectrum.c`）：

1. `ft8_spectrum_baseline()`：复刻 WSJT-X `lib/ft8/get_spectrum_baseline.f90` + `baseline.f90` —— 93 段 Nuttall 加窗 3840 点 FFT（df=3.125 Hz）平均 → 100–3000 Hz 内分 10 段取**第 10 百分位低包络** → 4 阶多项式拟合，得到逐频点噪声底 `sbase[f]`（dB）。每时隙只算一次。
2. `ft8_spectrum_snr()`：在精化位置累加 79 个符号的正确音调功率 `Σsig`，返回原始指标

```text
z = 10·log10( Σ_k sig_k ) − sbase[f]
（WSJT-X 原式：snr = 10·log10( xsig / xbase / 3e6 ) − 27，xbase = 10^((sbase−40)/10)）
```

3. `ft8api.c` 置 `snr_raw = z`，经 `FT8_SNR_CALIB_SLOPE/INTERCEPT = 1.0 / −94.6` 上报。斜率固定 1.0；偏移吸收信号功率/噪声底的量纲与窗归一差异，由 `test/` 全量命中对 WSJT-X 参考**斜率=1 偏移拟合**得到（WSJT-X 原式常数为 −51.77）。

> **口径说明**：`sbase` 是整时隙「无信号区域」的平滑噪声底，SNR 取决于信号功率与它的**比值**；斜率=1 时全量 MAE ≈ 3.5 dB（详见 §4.8）。

该步骤只对**已解码候选**执行。基线每时隙一次（93×3840 FFT）；单条命中另需 GFSK 精细对齐 + 79×8 Goertzel（≈15–30 ms），因此只在去重后对**实际上报的命中**计算一次并多线程并行（见 §3.6、§4.8）。

### 3.5 P2.3 设计：公共精细对齐 + 选择性 LLR 重解（评估）

**目标**：把已证明有效的精细对齐抽成公共模块，并把它用于 **BP 失败候选的 LLR 重算**，作为继 P2.1 OSD 之后的第二个召回杠杆。

#### 3.5.1 公共精细对齐 `ft8_align`

现状：`ft8_spectrum.c` 与 `ft8_subtract.c` 各有一套「相关 / 频偏估计 / 参考调制 / 粗-细对齐」，数学同源但**参数与策略不同**：

| 维度 | `ft8_spectrum`（`sp_align_refine`） | `ft8_subtract` |
| --- | --- | --- |
| 粗搜 | 非相干多符号（12 符号）+ 音调消歧（±2×6.25 Hz） | 相干 3 符号 |
| 细搜范围 | ±24 样本 | ±48 样本 |
| Δf 钳制 | 3.0 Hz | 5.0 Hz |

方案（**先保证不改解码文本**，分两步）：

1. **纯重构**：新建 `native/api/ft8_align.{h,c}`，抽出共享原语 `ft8_align_correlate / ft8_align_correlate_nc / ft8_align_estimate_df / ft8_align_modulate_ref`，并把 `sp_align_refine` 原样搬为 `ft8_align_refine()`。`ft8_spectrum.c` 改为调用它 —— 参数不变则结果应**逐位一致**，由全量回归（基线 1062/236/43）确认。
2. **收敛 subtract（可选，需 A/B）**：让 `ft8_subtract` 改用公共原语（保留其相干粗搜策略与参数）；若进一步采用 spectrum 的对齐策略可能提升消除质量，但会改变残差进而改变解码文本，**必须先 A/B 全量对比**（召回/extra/文本），无退化才合并。

> 开放问题（待定）：是否让 subtract 采用 spectrum 的「音调消歧 + 非相干粗搜」。收益是可能改善弱信号消除，风险是改文本；P2.3 先完成步骤 1。

#### 3.5.2 `ft8_spectrum_llr`（解码前时域精化 LLR）

关键约束：**重解发生在解码之前，数据音调未知**，因此不能用 §3.5.1 那种需要全部 79 个已知音调的 `ft8_align_refine`。对齐只能依赖**已知的 Costas 同步音调**（3 组 × 7 个，`kFT8_Costas_pattern`）。

```c
int ft8_spectrum_llr(const float* samples, int num_samples, int sample_rate,
                     float freq0, float dt, float* log174);
```

流程：

1. **频率精化**：在 `freq0 ± 2 Hz`、步长 0.25 Hz 上搜索，使 21 个 Costas 符号在各自已知音调处的 Goertzel 功率之和最大；
2. **时间精化**：在 `±nsps/8` 样本、步长 4 上搜索，同样最大化 Costas 音调总功率，得样本级 `n0*`；
3. 在精化位置对 58 个数据符号做 1 符号窗 8 音调 Goertzel（复用 `tone_powers`），得 `p8[8]`；
4. 转功率 dB（与瀑布域 `WF_ELEM_MAG` 同量纲：`10·log10(p)`）；
5. 按 `kFT8_Gray_map` 与 `ft8_extract_symbol` 相同的 `max4` 组合，每符号得 3 个 LLR；数据符号下标 `sym = k + (k<29?7:14)`，共 174 个；
6. 失败（参数无效/内存不足）返回 -1。

#### 3.5.3 选择性重解接入（`decode.c` + `ft8api.c`）

在 `decode.c` 新增带「LLR 重算回调」的候选解码入口：

```c
typedef int (*ftx_refine_llr_fn)(void* ctx, const ftx_candidate_t* cand, float* log174);
bool ftx_decode_candidate_ex(const ftx_waterfall_t* wf, const ftx_candidate_t* cand,
                             int max_iterations, int osd_depth,
                             ftx_refine_llr_fn refine, void* refine_ctx,
                             int refine_min_errors,
                             ftx_message_t* message, ftx_decode_status_t* status);
```

级联顺序（任一步成功即返回）：

1. 瀑布域 LLR → `bp_decode`；
2. BP 失败且满足门控（`score ≥ FT8_OSD_MIN_SCORE`、`ldpc_errors ≤ refine_min_errors`、`refine != NULL`）→ 回调得精化 LLR → `ftx_normalize_logl` → 再 `bp_decode`；
3. 仍失败 → 用**精化 LLR（若有）优先**做 OSD（沿用 `osd_depth` / `FT8_OSD_*` 门限）；
4. 否则失败。

`ft8api.c` 的 `decode_worker` 已按候选分块多线程并行：把 `samples/num_samples/sample_rate` 随 `decode_worker_arg_t` 传入，回调内调 `ft8_spectrum_llr`。新增 `ft8_decode_config_t.enable_llr_refine`（默认 0；P2.3 先用 CLI `--llr-refine` 验证后再定默认）。

#### 3.5.4 成本、门控与验收（实测结论：负结果，默认关闭）

- 门控：仅 **BP 失败**且 `score ≥ FT8_OSD_MIN_SCORE`、`ldpc_errors ≤ refine_min_errors` 的候选触发；每 worker 每次 `decode_pass` 上限 `FT8_LLR_REFINE_BUDGET = 12` 次精化。
- **加性级联**：精化尝试放在瀑布域 BP + OSD **之后**，因此功能开启时召回只增不减，不会改变任何既有成功结果（首版曾把精化放在 OSD 之前，导致精化 BP 抢占 OSD 的正确结果、召回反降 1062→1048，已修正）。
- **全量实测（`test/` 1298 条，主机 4 线程，`--subtract --depth 3`）**：

  | 配置 | 命中 | 漏解 | extra | Recall | 耗时 avg / P95 |
  | --- | --- | --- | --- | --- | --- |
  | 关闭（基线） | 1062 | 236 | 43 | 81.8% | 252 / 341 ms |
  | **开启** | 1062 | 236 | **44** | 81.8% | **620 / 746 ms** |

- **结论：负结果**。1 符号时域精化 LLR 相对瀑布域（2 符号 Hann + 1.5625 Hz 网格）没有召回增益，仅新增 1 条 extra 与约 2.5 倍耗时。原因：数据段真正的召回瓶颈是需要 **AP 提示**的弱信号，而瀑布域的时频分辨率并不劣于单符号矩形窗。
- 因此 `enable_llr_refine` **默认 false**，仅保留为实验开关（CLI `--llr-refine` / JNI `DC_ENABLE_LLR_REFINE`），供后续换用更强的 LLR 估计（如 2/3 符号联合、多候选合并）时复用该级联框架。

### 3.6 性能预算（P2.2 实测）

| 步骤 | 成本（设备实测） |
| --- | --- |
| `ft8_spectrum_baseline`（93 段 3840 点 FFT + 低包络拟合） | 每遍每时隙一次 |
| `ft8_spectrum_snr`（GFSK 精细对齐 + 79×8 Goertzel） | ≈ 15–30 ms/条 |
| 每时隙调用次数 | 去重后 ≈ 16（原逐候选 ≈ 73） |
| **旧 7 音调口径整时隙** | avg 241 ms / P95 316 ms |
| **频谱噪声底口径整时隙** | **avg 275 ms / P95 372 ms / max 470 ms**（Android x86_64，4 线程，`--subtract --depth 3`） |

- 关键优化：SNR 只在 `decode_pass` 合并去重后对「首次出现」的命中计算，并由 worker 线程池并行，避免跨遍/遍内重复候选的浪费（全量调用 5010 → 1096 次）。
- 噪声底每遍每时隙算一次（多遍消除时最多 3 次），是相对旧口径新增的主要开销（≈ +35 ms avg / +56 ms P95），仍在 P95 ≤ 500 ms 预算内。
- 精细对齐参数经实测：粗搜范围 ±2400 样本不可收窄（收窄到 ±480 会使 R² 由 0.51 降到 0.25）。

## 4. 专项 B：OSD 兜底译码

### 4.1 原理（Ordered Statistics Decoding）

BP 是迭代概率译码，低 SNR 下可能不收敛。OSD 利用 **LLR 的可靠性排序 + 码的线性代数结构**，先在「最可靠的 91 个位置（信息集）」上求一个合法码字，再按可靠性从低到高做有限深度比特翻转搜索，用 CRC 作为接受门限。二者互补：先 BP，失败再 OSD。

### 4.2 可用素材（已在 MIT 基座内）

- `kFTX_LDPC_generator[83][12]`：系统生成矩阵 `G = [I₉₁ | P]`（前 91 位即消息位），可用于任意信息的快速重编码 `encode174`；
- `kFTX_LDPC_Nm[83][7]` + `kFTX_LDPC_Num_rows`：校验矩阵 `H`，用于高斯消元求最可靠基。

### 4.3 算法流程（自研 C，`native/api/ft8_osd.{h,c}`）

输入：174 个 LLR（来自现有瀑布或专项 A）。

1. **可靠性排序**：按 `|LLR|` 降序得位置置换 `π`；硬判决 `y[i] = (llr[i] > 0)`（与 `bp_decode` 同一约定）。
2. **求最可靠基（MRB）**：取前 91 个最可靠位置 `S`，在 GF(2) 上对 `H` 的 `S` 列做 Gauss-Jordan 消元，解出使码字与 `y` 在 `S` 上一致的信息 `m`（等价于 `91×91` 线性方程求解）。若 `S` 奇异，按顺序与后一位交换再试。
3. **Order-0**：`c = encode174(m)`，CRC 校验；通过即返回（`ap_type=0`）。
4. **Order-s 重处理**：对可靠性最低的若干位置（非 MRB 部分）枚举重量 ≤ `osd_depth` 的错误图样 `e`，令 `y' = y ⊕ e` 重解 `m`、重编码、CRC 校验；命中即返回。
5. **上限保护**：翻转组合数与耗时设硬上限（如 order-2 采样上限），超限即放弃，保证时延。

### 4.4 级联顺序

```text
coarse LLR → bp_decode
    ├─ 成功 → CRC → 输出
    └─ 失败 → (可选) 专项 A 重算 LLR → bp_decode 重试
                         └─ 仍失败 → OSD(order-0..N) → CRC → 输出
```

### 4.5 AP 扩展（可选，与 OSD 同框架）

已知 `my_call` / `his_call` / `his_grid` 时，将对应信息位置的信度强制为高值（或固定为已知比特），再走 OSD；命中后上报 `ap_type`。这是 `ap_mode` 字段的落地，P2 可作为 OSD 的附加开关。

### 4.6 配置

新增 `osd_depth`（0=关闭，1..3=阶数）；CLI 加 `--osd N`，**默认 2**（平衡召回与 extra，见 §4.7）。仅对 BP 失败候选触发；`osd_depth=0` 时完全不影响 P1 行为。

### 4.7 P2.1 实测、门限固化与缺陷修复（2026-10-02）

**接受语义缺陷（已修复，重要）**：初版 `ft8_osd_decode()` 返回「尝试过的码字数」（恒 ≥1），而调用方 `ftx_decode_candidate_osd()` 把任何非零返回都当作「已接受」，导致 OSD 未命中时返回真，并把**未初始化的 `message`/`status`** 当作结果上报。表现为：
- 出现 `6H7L W-`、`Error [5] while unpacking!` 等「幻影消息」，且同一候选在 `--threads 1/2/4` 下结果不同（实为栈上残留的、来自其他候选的垃圾消息，随内存布局变化）；
- extra 虚高（depth3 曾达 ~151 条）。

修复：`ft8_osd_decode()` 改为**命中返回 1、否则返回 0**（不再返回尝试次数）；`decode_worker()` 对 `message`/`status` 显式初始化；并在 `decode_pass()` 合并阶段**丢弃 CRC 通过但无法解包（`Error [N]`）或空文本的码字**，避免其污染后续信号消除。

**门限固化**（`native/src/decode.c`，已用全量 1298 条扫参调定）：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `FT8_OSD_MAX_BP_ERRORS` | 12 | BP 残余校验错误数上限，超过不触发 OSD |
| `FT8_OSD_MAX_HARD` | 40 | OSD 码字与硬判决的汉明距离上限（≤0 不限制） |
| `FT8_OSD_MIN_SCORE` | 12 | 候选 Costas 同步分下限 |

扫参结论：`bperr` 由 24 收到 12，召回不变而 extra 减少约 4 条；`nhard=40` 已接近「不限制」的召回，再放宽只增 extra；`minscore=12` 在不损失召回的前提下去掉少量噪声候选。（调试用环境变量 `FT8_OSD_BPERR/NHARD/MINSCORE` 已移除。）

**P2.1 全量回归**（Android x86_64 模拟器，4 线程，`test/` 60 文件 / 1298 条，门限固化后默认值）：

| OSD 阶数 | 命中 | 召回率 | extra | P50 | P95 |
| --- | --- | --- | --- | --- | --- |
| 0（P1 基线） | 1048 | 80.7% | 37 (2.9%) | 187.7 ms | 231.4 ms |
| 1 | 1060 | 81.7% | 41 (3.2%) | 191.7 ms | 229.1 ms |
| **2（默认）** | **1062** | **81.8%** | **43 (3.3%)** | 191.1 ms | 233.9 ms |
| 3 | 1064 | 82.0% | 44 (3.4%) | 190.2 ms | 232.6 ms |

结论：达到 §8 的 P2.1 判据（召回提升、extra ≤ 4%、P95 远低于 500 ms）。其中相当一部分 extra 经人工核对为**参考集漏收的真实信号**（如 `DM2DLG UR7HN`、`CQ G0OSK IO91`、`CQ 2E0PKK IO90` 等），故真实误码率低于表中数字。

### 4.8 P2.2 实测：频谱噪声底 SNR（2026-10-03，取代 7 音调口径）

**背景与变更**：初版 P2.2 用 JTDX 同源「7 音调平均」口径，对 WSJT-X 参考 R²=0.506、MAE≈5.6 dB。该口径把「其余 7 个音调」当纯噪声，受同一时隙邻近信号污染会**严重低估强信号 SNR**，故改为 **WSJT-X 同源频谱噪声底**口径（§3.4）：`z = 10·log10(Σsig) − sbase[f]`，`sbase` 取自整时隙「无信号区域」的低包络；上报经 `1.0 / −94.6` 标定。

**实现**：

- `native/api/ft8_spectrum.c`：新增 `ft8_spectrum_baseline()`（93 段 Nuttall FFT 平均 → 10 段第 10 百分位低包络 → 4 阶拟合）；`ft8_spectrum_snr()` 在 `sbase` 非空时返回 `z`，为空则退回旧 7 音调口径（容错）。
- `native/api/ft8api.c`：`decode_pass` 内每遍计算一次噪声底并传入 SNR 批处理；`snr_order`（消除排序）仍用旧瀑布域口径，**不影响多遍消除行为**。

**全量回归**（`test/` 60 文件 / 1298 条，`--subtract --depth 3`）：

| 指标 | 旧「7 音调」口径 | **频谱噪声底口径** |
| --- | --- | --- |
| 命中 / 漏解 / extra | 1062 / 236 (18.2%) / 43 (3.3%) | 1062 / 236 (18.2%) / 43 (3.3%) |
| Recall | 81.8% | 81.8%（**解码文本不变**） |
| 参考回归（对 WSJT-X txt） | R²=0.506（斜率 0.795） | **R²=0.791**（斜率 0.836） |
| 斜率=1 偏移后 MAE / RMSE | 5.4 / 7.3 dB | **3.5 / 5.0 dB** |
| ±1 / ±2 / ±3 dB 命中率 | 12% / 24% / 36% | **21% / 41% / 54%** |

**结论**：

- 换用「无信号区域」噪声底后，对 WSJT-X 参考 R² 由 0.51 → **0.79**、MAE 由 5.4 → **3.5 dB**、分档命中率约翻倍；召回/extra/文本完全不变。
- 标定斜率固定 **1.0**（全量实测斜率 0.836；强制 1 后 MAE 几乎不劣），仅用一个恒定偏移，物理上对应「信号功率/噪声底的量纲与窗归一差」（WSJT-X 原式常数为 −51.77）。
- 失败容错：噪声底计算失败时自动退回 7 音调口径，上报不会缺失。
- 备选：若需完全逐位复刻 WSJT-X，可进一步移植其 `ft8_downsample`（信号功率走下变频 32 点 FFT），使斜率趋近 1；当前以「换噪声估计」为限。

## 5. 专项 C：NEON 加速

### 5.1 目标热点（按收益排序）

1. `monitor_process`：`mag2 = re²+im²` 与 `db = 10·log10` + 量化（每时隙数百次 FFT 后逐 bin）；
2. LLR 提取的 `max` 运算（`ft8_extract_symbol` / `ft8_decode_multi_symbols`）；
3. 专项 A 的 Goertzel / 窄带 DFT；
4. BP 的 `fast_tanh` / `fast_atanh`（图不规则，向量化收益有限，优先级最低）。

### 5.2 方案

- 以 `#if defined(__ARM_NEON) || defined(__ARM_NEON__)` 条件编译，`#include <arm_neon.h>`；**始终保留标量回退**，保证 x86_64 主机与模拟器一致；
- `mag2` 用 `float32x4` 乘加；`log10` 用多项式近似（保留与 `log10f` 的误差界校验）；
- LLR 的 8 音调 max 用向量归约；
- 仅 `-O3`，**不引入 `-ffast-math`**（避免改变数值行为、影响 CRC 通过率的可复现性）；如需要可局部使用。

### 5.3 验收

- 结果与标量版**逐条一致**（同输入同参数）；
- `arm64-v8a` 解码耗时较标量下降 ≥ 20%（模拟器先验证功能，真机验证性能）。

## 6. 专项 D：常驻线程池

### 6.1 现状

`decode_pass()` 每遍为 `num_threads` 个候选区间创建/join/销毁线程；对每遍 ~70 ms 的工作量，创建开销占比不大，但**实时流式下反复创建不利于抖动**，且限制了对 OSD 等子任务的细粒度并行。

### 6.2 方案

- `native/api/ft8_pool.{h,c}`：惰性创建的常驻线程池（POSIX `pthread` + `sem`/`cond`，Win32 `CreateThread`+事件），提供 `submit(fn,arg)` / `wait_all()`；
- `ft8_decode_slot` 与会话持有池实例（会话跨时隙复用）；
- `num_threads<=1` 时**不创建任何线程**，保持串行路径与默认行为完全不变；
- 工作划分由「静态区间」升级为「原子任务队列」，改善候选耗时不均时的负载均衡。

### 6.3 验收

- 默认配置结果与 P0/P1 完全一致；
- 多线程下 P50/P95 不劣于现状，小任务（候选少）延迟下降。

## 7. API 与配置变更

新增字段一律**追加**到 `ft8_decode_config_t` 末尾，保持既有字段偏移与 JNI 兼容：

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `osd_depth` | OSD 阶数（0=关闭） | 2 |
| `enable_llr_refine` | BP 失败候选用时域精化 LLR 重解（P2.3） | false |

**语义澄清（重要）**：`decode_depth` 当前在 P1 实现中表示**多遍消除的遍数**，与 `ft8api.h` 旧注释「0=基础/1=+OSD/2=+多遍/3=+AP」不一致。P2 统一定义为「多遍消除遍数」，OSD 改由 `osd_depth` 控制，并同步更新 `ft8api.h`、`docs/00` 与 JNI 注释。

JNI `DC_*` 枚举末尾追加 `DC_OSD_DEPTH`、`DC_ENABLE_LLR_REFINE`；`read_decode_cfg` 已按数组实际长度裁剪，旧 Kotlin 传短数组仍安全。

结果结构 `ft8_message_result_t` 不变（`ap_type` 已预留）。

## 9. 验证方法

1. **合成用例**：用 `ft8_cli gen` 生成低 SNR（逐步加噪）信号，构造「BP 失败、OSD 成功」的样本；生成碰撞样本验证与消除的协同。
2. **全量回归**：`ft8_cli bench test` 固定参数，逐项对比 P1 的召回率、extra、P50/P95。
3. **消融**：`osd_depth=0/1/2/3`、`enable_refine` 开/关、NEON 开/关，各自独立测量。
4. **SNR 校验**：回归斜率/截距/R² + 逐条误差分布，替换现有标定常量。
5. **真机**：`arm64-v8a` 复测 P95（模拟器 x86_64 不代表手机）。
6. **原始记录**：结果落盘 `test_results/`，并写入 `docs/02-测试报告.md`。

## 10. 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| OSD 计算量大 | 超时延预算 | 仅失败候选触发；阶数与组合数硬上限；先 OSD-0/1 |
| OSD 误纠导致 extra 上升 | 虚假解码 | CRC-14 强门限；监控 extra，超 4% 则收紧 |
| 逐符号 LLR 重解成本高 | 超预算 | 选择性触发 + Top-K 门控；必要时仅保留 SNR |
| NEON 与标量结果不一致 | 回归偏移/难排查 | 保留标量路径；逐条一致性测试 |
| `decode_depth` 语义变更 | 接口歧义 | 文档与注释统一；新增独立 `osd_depth` |
| 精细对齐抽公共模块引入回归 | P1 相减质量下降 | 抽出后先做 P1 回环与全量回归，确保无变化 |
