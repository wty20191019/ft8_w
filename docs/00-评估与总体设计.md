## 1. 目标与约束

### 1.1 产品目标（来自需求）

| 维度 | 目标 | 对标对象 |
| --- | --- | --- |
| 解码能力 | 与 JTDX 同档：弱信号、多信号、多径/忙段下的解码数量与灵敏度 | JTDX |
| 操作界面 | 交互逻辑、布局、工作流 | FT8CN |
| 电台控制 | **仅使用 VOX**，不依赖 CAT/串口 PTT | —— |

### 1.2 本阶段（C 层）目标

1. 实现一套 **FT8 解码 / 编码** 的 C 模块，可独立编译、可单元测试。
2. 通过 **JNI 桥** 暴露给 Kotlin。
3. 暴露 **影响解码/编码的所有关键参数**，以及必要的输入输出结构。
4. **单时隙（15s 音频）解码耗时 ≤ 1000 ms，力争 ≤ 500 ms**；允许使用多线程。

### 1.3 硬性工程约束

- 目标平台：Android（`arm64-v8a` 主，`armeabi-v7a` / `x86_64` 备）。
- 工具链：Android NDK r28 + CMake（本机已具备 `ndk/28.2.13676358` 与 `cmake/3.22.1`）。
- 音频采样率默认 **12000 Hz**，单声道，16-bit。
- VOX 发射：编码侧只负责产出「音频波形 + 前后静音保护间隔」，不涉及 CAT。

## 2. 参考仓库评估

工作区内已有三块素材：

| 目录 | 内容 | 语言 | 许可证 |
| --- | --- | --- | --- |
| `ft8_lib/` | 轻量 FT8/FT4 编解码库（含 kissfft、monitor、message、demo、测试集） | C | **MIT** |
| `jtdx/` | 完整 JTDX 桌面端（含 Fortran 解码核心、LDPC、OSD、packjt77 等） | Fortran/C++ | **GPLv3** |
| `test/` | 67 个 15s WAV 测试音频 + 逐条对照文本（`test_01..38`、`websdr_test*`、`191111_*`） | 数据 | —— |

### 2.1 `ft8_lib`（MIT，作为 C 层实现基座）

优点：

- 纯 C、结构清晰、依赖极少（自带 kissfft），易移植到 Android。
- 完整覆盖：STFT 瀑布、Costas 候选搜索、LLR 提取、LDPC(BP) 译码、CRC-14、77-bit 消息打包/解包、GFSK 波形合成。
- 自带测试集与对照工具，便于建立回归基线。
- **MIT 许可证**，商业/闭源友好。

不足（相对 JTDX）：

- 单遍解码（single-pass），没有对已解码信号的**时域消除重解**（multi-pass subtraction）。
- 没有 **AP（a priori，已知呼号辅助）解码**，弱信号灵敏度有差距。
- 没有 **OSD（Ordered Statistics Decoding）** 兜底。
- 候选排序/比特度量较简化，忙段（20m busy）解码数明显少于 JTDX。
- 缺少 JTDX 的「哈希呼号缓存 / 非标准呼号 / 比赛模式」等完整消息集（部分已具备）。

### 2.2 `jtdx`（GPLv3，作为**算法对标与参考**，不直接搬运）

关键可借鉴能力（`jtdx/lib/ft8b.f90`、`ft8_decode.f90`、`ft8v2/*`）：

- **多遍解码 & 信号消除**：`lsubtract` / `lft8subpass`，解出的信号重合成后从时域减去再解。
- **AP 解码**：`apsym*`、`apmask`，用 `mycall/hiscall/hisgrid` 先验约束部分比特，提高灵敏度。
- **深度同步**：`ldeepsync`、`nthr`、`ncandthin` 等分级候选策略。
- **LDPC 迭代上限 30**，配合 `bpdecode174_91` 与 `osd174_91`（OSD 多阶）。
- **消息打包**：`packjt77.f90`（比赛/遥测/自由文本/非标准呼号，最全）。

> ⚠️ **许可证风险**：JTDX 为 **GPLv3**。若直接复制其 Fortran/C 代码进本项目，本项目整体须以 GPLv3 开源。**首轮方案：以 MIT 的 `ft8_lib` 为基座，JTDX 仅作算法层面参考（自行用 C 重新实现），从而保持许可证自由。**

### 2.3 测试集评估

- 根目录 `test/` 与 `ft8_lib/test/wav/` 为同一套音频（约 67 个 15s 时隙）。
- 对照文本格式（WSJT-X/JTDX 输出风格）：
  `MMddHH  SNR  DT  Freq ~  文本  其他注解`
  例：`000000  -7  0.6  955 ~  CQ IU8DMZ JN70`
  - 前 6 位是时隙时间戳（测试集统一为 `000000`）。
  - `SNR`、`DT`、`Freq` 用于对齐，不计入文本匹配。
  - 末尾可能带国家/地区注释（如 `Italy`），解码文本本身在 `~` 之后。
- **测试用途**：解码文本命中率（Recall / Precision）作为「对标 JTDX」的量化指标。

## 3. 技术选型

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 实现语言 | C（C11） | 需求明确「C 层」；跨平台、JNI 友好、易做 DSP |
| 基座代码 | 复用/改造 MIT 的 `ft8_lib` 核心 | 成熟、许可证友好、已验证 |
| FFT | kissfft（随 `ft8_lib` 自带） | 无外部依赖；后续可换 NEON/FFTS 优化 |
| 消息打包 | `ft8_lib/message.c` + `text.c` | 已覆盖标准/非标准/自由文本/遥测 |
| 线程 | 自研极简线程封装（POSIX pthread / Win32 二选一） | Android 用 pthread，Windows 主机测试用 Win32 |
| 桥接 | JNI（C++ 层 `ft8_jni.cpp`） | Kotlin 调用，零拷贝可用 `DirectByteBuffer` 优化 |
| 构建 | CMake（NDK toolchain） | Android Gradle externalNativeBuild 标准做法 |
| 主机验证 | 主机 clang（winget LLVM）编译 CLI | 在 PC 上跑测试集 + 性能基准，快速迭代 |

### 3.1 为什么不用 Kotlin/Scala 直接实现

- 解码是数值密集型，C + 可能的 SIMD/NEON 才有性能保障。
- JTDX 同档算法（OSD/多遍消除）用 C 实现更易复用已有 C 参考。
- 音频采集在 Kotlin（AudioRecord），DSP/编解码在 C，是 Android SDR 类应用的通行架构。

## 5. C API 设计（`include/ft8api.h`）

设计原则：

- **对外只暴露 `ft8api.h`**，内部 `ft8_lib` 细节不泄漏。
- 参数集中在 `ft8_decode_config_t` / `ft8_encode_config_t`，便于 JNI 与后续 UI 暴露。
- 输入输出用**扁平结构体数组**，跨 JNI 零解析成本。
- 提供 **一次性（文件/整时隙）** 与 **流式（实时音频）** 两套接口。

### 5.1 解码配置（影响解码的全部参数）

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `f_min_hz` / `f_max_hz` | 分析频率范围 | 200 / 3000 |
| `sample_rate` | 采样率 | 12000 |
| `time_osr` | 时间过采样（1/2/4） | 2 |
| `freq_osr` | 频率过采样（1/2/4） | 2 |
| `max_candidates` | 最大候选数 | 140 |
| `min_sync_score` | 同步最低分（灵敏度/速度权衡） | 10 |
| `ldpc_iterations` | LDPC 迭代上限 | 25 |
| `decode_depth` | 0 基础 / 1 +OSD / 2 +多遍消除 / 3 +AP | 0 |
| `ap_mode` | AP 提示位掩码 | 0 |
| `my_call` / `his_call` / `his_grid` | AP 先验（可空） | NULL |
| `enable_subtract` | 多遍消除 | false |
| `num_threads` | 0/1 串行，>1 并行候选解码 | 1 |
| `return_duplicates` | 是否返回重复 | false |

### 5.2 解码输出

```c
typedef struct {
    char     text[48];   // 解码文本（UTF-8/NUL 结尾）
    float    snr;        // 估计 SNR (dB)
    float    dt;         // 时间偏移 (s)
    float    freq;       // 音频频率 (Hz)
    int      score;      // Costas 同步分
    int      ldpc_errors;// 0 表示 LDPC 校验通过
    int      pass;       // 第几遍解出（0 基）
    int      ap_type;    // AP 类型，0 = 无
    uint16_t crc;        // CRC-14
} ft8_message_result_t;
```

### 5.3 主要函数

```c
// 默认配置
void ft8_decode_config_default(ft8_decode_config_t* cfg);
void ft8_encode_config_default(ft8_encode_config_t* cfg);

// 一次性解码（整时隙音频，阻塞）
// 返回解码条数(>=0)，负数为错误码
int ft8_decode_slot(const float* samples, int num_samples,
                    const ft8_decode_config_t* cfg,
                    ft8_message_result_t* out, int max_out);

// 流式会话（实时音频逐块送入，时隙末 finalize）
ft8_decode_session_t* ft8_decode_session_create(const ft8_decode_config_t* cfg);
void ft8_decode_session_reset (ft8_decode_session_t* s);
int  ft8_decode_session_feed  (ft8_decode_session_t* s, const float* samples, int n);
int  ft8_decode_session_finalize(ft8_decode_session_t* s,
                                 ft8_message_result_t* out, int max_out);
void ft8_decode_session_free  (ft8_decode_session_t* s);

// 编码：文本 -> 音频 PCM
int ft8_encode_message(const char* message, const ft8_encode_config_t* cfg,
                       float* out, int max_samples); // out=NULL 时返回所需长度

// 编码：文本 -> 79 个音调（调试用）
int ft8_encode_tones(const char* message, uint8_t* tones);
```

### 5.4 编码配置（影响发射/波形）

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `sample_rate` | 波形采样率 | 12000 |
| `base_freq_hz` | 音调 0 的音频基准频率 | 1000 |
| `amplitude` | 幅度 0..1 | 0.5 |
| `symbol_bt` | GFSK 平滑系数 | 2.0 |
| `lead_in_sec` | 前导静音（VOX 起控保护） | 0 |
| `tail_sec` | 尾部静音（VOX 释放保护） | 0 |
| `int16_output` | 预留：直接输出 int16 | false |

## 6. JNI 桥设计

### 6.1 Kotlin 侧签名（规划）

```kotlin
object Ft8Native {
    init { System.loadLibrary("ft8") }

    // 返回所需采样点数；用于分配缓冲
    external fun encodeLength(message: String, cfg: FloatArray): Int
    // 返回实际写入的采样点数
    external fun encode(message: String, cfg: FloatArray, out: FloatArray): Int
    external fun encodeTones(message: String): ByteArray

    external fun decodeConfigDefault(): FloatArray   // 打包默认配置
    // 返回 [count, 之后每条 N 个 float/字段...] 或直接返回 String[]
    external fun decodeSlot(samples: FloatArray, cfg: FloatArray): Array<String>
    external fun decodeSlotDirect(samples: java.nio.FloatBuffer /*direct*/, len: Int,
                                  cfg: FloatArray): Array<String>

    // 流式
    external fun sessionCreate(cfg: FloatArray): Long
    external fun sessionFeed(handle: Long, samples: FloatArray): Int
    external fun sessionFinalize(handle: Long): Array<String>
    external fun sessionDestroy(handle: Long)
    external fun version(): String
}
```

### 6.2 参数封送约定（首轮）

- `cfg: FloatArray` 用**定长 float 数组**承载配置（int 也按 float 传），避免引入 JSON 解析：
  - 解码：`[f_min, f_max, sample_rate, time_osr, freq_osr, max_candidates,
    min_sync_score, ldpc_iterations, decode_depth, ap_mode, enable_subtract,
    num_threads, return_duplicates, ...]`
  - 编码：`[sample_rate, base_freq, amplitude, symbol_bt, lead_in, tail_sec]`
- 结果为 `Array<String>`，每条消息用 **`\u0001`（或 `|`）分隔字段**：
  `text|snr|dt|freq|score|ldpc_errors|pass|ap_type|crc`
  Kotlin 侧一个扩展函数即可映射为 `data class Ft8Message`。
- 后续若字段增多，可改为返回 `DirectByteBuffer` 里的紧凑二进制（吞吐更高）。

### 6.3 线程与 JNI

- **不在 JNI 层再起 Java 线程**：`ft8api` 内部按 `num_threads` 起原生工作线程。
- JNI 调用 `ft8_decode_slot` / `session_finalize` 期间会阻塞；Kotlin 侧放到协程 `Dispatchers.Default` 或专用线程。
- 长耗时可选择性加 `AtomicBoolean` 取消标志（后续版本）。

## 7. 性能预算与多线程策略

### 7.1 单时隙工作量拆解（12 kHz，15 s，时/频 OSR=2）

| 阶段 | 规模 | 备注 |
| --- | --- | --- |
| STFT | 158 次 FFT(3840 点) | 79 符号 × time_osr=2 |
| 候选搜索 | ~5.4 万候选 × 21 同步符号 | 可优化，通常 10–30 ms |
| LLR 提取 | ≤ `max_candidates` × 174 | 轻量 |
| LDPC(BP) | ≤ 140 候选 × 25 迭代 | **主要开销**，用多线程并行 |
| CRC + 解包 | ≤ 命中条数 | 轻量 |
| （P1）多遍消除 | 重合成 + 重 STFT | 视深度，仅在有解码时触发 |

### 7.2 达到 ≤500 ms 的策略（按优先级）

1. **候选解码多线程**：把候选按分数排序后分块，N 核并行 BP；近似线性加速。首轮即实现。
2. **早停**：BP 一旦 `errors==0` 立即退出（`ft8_lib` 已有）。
3. **分级候选**：先高 `min_sync_score` 快速解一遍，再降低阈值补解（JTDX 的 `ncandthin` 思想）。
4. **限制 LDPC 迭代**：默认 25；慢机可降到 15。
5. **内存布局 / 缓存友好**：BP 用固定小矩阵（`ft8_lib` 的 `tov/toc` 已是紧凑布局）。
6. **NEON/SIMD**：后续对 LLR 提取与 `tanh` 近似向量化。
7. **避免重复分配**：会话对象复用瀑布缓冲区。

### 7.3 并行模型

```
主线程:  monitor_process(音频块) → 瀑布
         ftx_find_candidates()  → 候选列表(按分数降序)
   ├─ worker 0: decode candidates[0..k)
   ├─ worker 1: decode candidates[k..2k)
   └─ worker N: ...
主线程:  收集结果 → 去重(按 hash) → 解包文本 → 输出
```

- 工作线程按「候选区间」划分，天然无锁；结果写各自局部数组，主线程合并。
- 线程数默认 `min(4, 大核数)`，用户可配。

## 8. 与 JTDX 的差距与分阶段路线

| 能力 | `ft8_lib`(基座) | JTDX | 本方案 |
| --- | --- | --- | --- |
| 基础解码 | ✅ | ✅ | P0 ✅ |
| 多线程 | ❌ | ✅ | **P0 ✅** |
| 多遍信号消除 | ❌ | ✅ | P1 |
| AP 呼号辅助 | ❌ | ✅ | P1 |
| OSD 兜底 | ❌ | ✅ | P2 |
| 比赛/遥测完整打包 | 部分 | ✅ | P1–P2 |
| 深度同步/分级候选 | 简化 | ✅ | P1 |
| JTDX 同档解码数 | 明显偏低 | 基准 | P1 后逐步逼近 |

**阶段定义**

- **P0（本次交付）**：可编译 C 库 + JNI 桥 + 完整参数/IO + 多线程 + 主机 CLI + 回归测试脚本；基础解码达到 `ft8_lib` 水准，满足 ≤1s / 力争 ≤500ms。
- **P1**：多遍消除（时域重合成相减）、AP 解码、分级候选、呼号哈希完整化。
- **P2**：OSD、NEON 优化、比赛/遥测消息全集。
- **P3**：Android 端 AudioRecord 集成、VOX 发射时序、UI（FT8CN 风格）。

> 「对标 JTDX」在 P0 阶段的目标是**建立可量化基线**（解码命中率、时延），而非宣称已达到。P1 起逐项收敛差距。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| JTDX 为 GPLv3，误引用会传染 | 许可证 | 只做算法参考，自行 C 实现；引入即整体 GPL，需产品决策 |
| Android 无成熟主机编译器 | 无法快速回归 | 用 NDK clang 交叉编译 + 主机 clang CLI 双轨 |
| BP 在低端机超时 | 体验 | 多线程 + 降迭代 + 分级候选 + 超时截断 |
| 浮点性能差异大 | 基准失真 | 基准同时报「PC 主机」与「Android 真机」两组数据 |
| 音频 IO 抖动 | 解码起点漂移 | 时隙对齐 + `dt` 搜索范围 ±2s；流式会话按块累积 |
| 内存峰值（瀑布） | OOM | 瀑布 uint8 量化，单时隙约 79×2×2×448 ≈ 0.28 MB，可忽略 |

## 10. 验收标准与测试方案

### 10.1 功能验收

1. `ft8_encode_message("CQ JA1ABC PM95")` 生成 15s 波形，`decode` 能自解（回环）。
2. 对 `test/` 全量 WAV 解码，输出文本与对照 `*.txt` 的**命中率**报告。
3. JNI 桥在 Android 上可 `System.loadLibrary("ft8")` 并完成一次 encode/decode 往返。

### 10.2 性能验收

| 指标 | 目标 |
| --- | --- |
