# FT8 C 层（P0）测试报告

> 阶段：P0（基础编解码 + 多线程 + JNI + CLI）
> 日期：2026-10-02
> 结论：**功能正确、性能大幅达标**；P1（多遍信号消除）+ P2.1（OSD 兜底）+ P2.2（逐符号频谱 SNR）后召回率 81.8%、extra 3.3%、P95≈316 ms；`SNR` 采用 JTDX 同源 7 音调平均口径（对 WSJT-X 参考 R²≈0.51，属口径差异，见 §7.5）。

---

## 1. 测试目标

1. 验证 C 层编解码功能正确（编码 → 解码回环、真实 WAV 解码）。
2. 量化解码召回率（Recall），建立可对比基线。
3. 量化单时隙解码耗时，验证满足「≤1000 ms，力争 ≤500 ms」。
4. 验证多线程并行有效性。
5. 验证 JNI 桥与 Android 侧可加载性。

## 2. 测试环境

| 项 | 值 |
| --- | --- |
| 目标平台 | Android `x86_64`（`emulator-5554`，Pixel_10_Pro，android-24） |
| CPU | 4 vCPU（`/proc/cpuinfo` 报告 4） |
| NDK | `28.2.13676358` |
| 构建 | CMake 3.22.1 + Ninja，`Release`，`-DFT8_BUILD_CLI=ON` |

> 说明：模拟器 `x86_64` 不能代表 ARM 手机性能，真机（`arm64-v8a`）数据待补（见 §8）。本报告数值用于验证「功能正确性」与「量级达标」。

## 3. 测试方法

- **测试集**：`test/` 下 69 个 WAV（单声道 16-bit PCM，多数 12000 Hz / 15 s），其中 60 个带对照 `*.txt`。
- **对照语义**：与 `ft8_lib/utils/run_tests.py` 对齐——取参考行 `~` 之后的文本，比较前 3 个 token；`<...>` 归一化为 `<...>`。
- **解码参数（默认，与上游 `decode_ft8` demo 完全一致）**：
  `f_min=200 Hz, f_max=3000 Hz, time_osr=2, freq_osr=2, max_candidates=140, min_sync_score=10, ldpc_iterations=25`。
- **命令**：
  ```
  ft8_cli bench . --threads {1,2,4} --repeat 3
  ```

## 4. 结果一：解码召回率

| 指标 | 数值 |
| --- | --- |
| 文件数（有对照） | 60 / 69 |
| 期望消息数 | 1298 |
| 命中（matched） | 942 |
| 漏解（missed） | 356（27.4%） |
| 多余（extra） | 26（2.0%） |
| **召回率 Recall** | **72.6%** |

逐文件结果见 `test_results/android_x86_64_threads4.txt`。代表性样例：

| 文件 | 命中/期望 | 耗时 |
| --- | --- | --- |
| `test_16.wav` | 16/16 | 17.3 ms |
| `websdr_test4.wav` | 21/23 | 10.5 ms |
| `191111_110645.wav` | 17/20 | 9.6 ms |
| `test_21.wav` | 19/34 | 15.2 ms |
| `test_05.wav` | 20/32 | 10.5 ms |

**漏解归因**（以 `test_21` 为例人工核对）：漏解集中在两类——

1. **频率相邻的碰撞信号**：如 2378 Hz 的 `CQ SP9LKP JO90`（参考 +13 dB）与 2389 Hz 的 `CQ E75C JN93` 仅相距约 10 Hz，单遍解码只解得后者；1652 Hz 的 `CQ RX6DA KN85` 被 1678 Hz 的 `CQ F6HUK JN06` 压制。
2. **弱信号 / 低信噪比**：参考 SNR ≤ −17 dB 的多条消息未解出。

这与 `ft8_lib` 单遍解码的固有能力一致，**不是实现缺陷**；JTDX 的优势主要来自多遍「重合成相减 + AP 辅助解码」，正是 P1 的内容。

## 5. 结果二：解码性能

单时隙（15 s 音频，含 STFT + 候选搜索 + LDPC）耗时：

| 线程数 | avg | P50 | P95 | max |
| --- | --- | --- | --- | --- |
| 1 | 14.4 ms | 14.8 ms | 16.0 ms | 16.3 ms |
| 2 | 12.6 ms | 12.9 ms | 13.9 ms | 15.1 ms |
| 4 | 9.7–10.8 ms | 9.8–10.2 ms | 10.5–15.2 ms | 10.5–17.6 ms |

> 4 线程列为多次运行区间；模拟器调度抖动导致 P95/`max` 波动，`P50` 稳定在约 10 ms。

- **P95 ≈ 10–15 ms（4 线程）**，远低于「≤1000 ms」硬指标，也大幅优于「≤500 ms」期望值。
- 并行加速为次线性（1→4 线程约 1.4×）：单次解码工作量仅约 10–15 ms，线程创建/汇合与模拟器调度开销占比偏高。
- 注：库内例行日志（`Block size`/`N_FFT`）已从 `LOG_INFO` 降为 `LOG_ERROR`，此前它位于计时区内，会额外引入约 8 ms/文件的 `fprintf` 开销。

**后续优化方向（P2）**：使用常驻线程池替代「每次解码创建线程」，可进一步降低小任务下的并行开销。

## 6. 结果三：编码回环与 JNI

- **编码 → 解码回环**：`gen "CQ JA1ABC PM95"`（1200 Hz）后解码，精确还原 `CQ JA1ABC PM95`（+19 dB，freq=1200 Hz，dt=+0.2 s）。✅
- **CLI 退出码**：成功 0，参数错误 2。✅
- **JNI**：`ft8_jni.cpp` 已通过 NDK clang `-fsyntax-only` 与链接检查；`libft8.so` 已成功产出（`build-android/`）。Android 侧 `System.loadLibrary("ft8")` 一次 encode/decode 往返尚待在示例 App 中联调（P3 UI 阶段）。

## 7. 已知问题与差距

### 7.1 SNR 估计：P0 占位 → P2.2 逐符号频谱（JTDX 7 音调平均口径）

P0 曾由同步分近似 `snr = score * 0.5`（上游 `ft8_lib` demo 的 TODO），输出恒为 **+10 ~ +18 dB**、与真实信噪比几乎不相关。

P2.2 已改为 `ft8_spectrum_snr()`：在候选精化位置上对 79 个符号逐一做 8 音调窄带 DFT，按 JTDX `ft8b.f90:1636-1655` 的 7 音调平均口径计算

```
raw = 10*log10(mean_k(sig_k / noise_k) - 1) - 26.5     // noise_k = 其余 7 音调均值
```

并套用与 JTDX 一致的高/低 SNR 分段修正。上报值 `snr_raw` 与消除排序值 `snr_order` 分离（后者保留旧瀑布域口径以稳定多遍消除）。标定常量 `FT8_SNR_CALIB_SLOPE/INTERCEPT = 1.0/0.0`。

**口径说明**：WSJT-X 上报用的是「平均频谱低包络基线」（`sbase`），JTDX 用 7 音调平均，二者对同一信号本就不同源；本项目**对标 JTDX**，故不向 WSJT-X 参考 txt 拟合（实测见 §7.5）。

| AP 呼号辅助解码 | ✗ | ✗ | ✗ | ✓ |
| 深度/分级候选 | 简化 | 简化 | 简化 | 完整 |

P1（多遍信号消除）已完成并在模拟器全量回归，详见 `docs/03-P1-信号消除设计.md` §10。

### 7.3 主机 A/B 基线未完成

主机 LLVM 已安装（`clang 23.1.2`），但 `ft8_lib` 原版 A/B 尚未执行。当前「以 `ft8_lib` 为基线不劣化」的论证依据是：**核心源文件与参数配置和上游 `decode_ft8` demo 完全一致**，因此召回率即为 `ft8_lib` 基线值。待主机 A/B 跑通后，用原始 `decode_ft8` 复跑同一测试集做直接对比。

### 7.4 P2.1 · OSD 兜底译码回归（2026-10-02）

门限固化（`bperr≤12 / nhard≤40 / score≥12`，见 `docs/04` §4.7）后，Android x86_64 模拟器、4 线程、`test/` 60 文件 / 1298 条：

| OSD 阶数 | 命中 | 召回率 | extra | P50 | P95 |
| --- | --- | --- | --- | --- | --- |
| 0（P1 基线） | 1048 | 80.7% | 37 (2.9%) | 187.7 ms | 231.4 ms |
| 1 | 1060 | 81.7% | 41 (3.2%) | 191.7 ms | 229.1 ms |
| **2（默认）** | **1062** | **81.8%** | **43 (3.3%)** | 191.1 ms | 233.9 ms |
| 3 | 1064 | 82.0% | 44 (3.4%) | 190.2 ms | 232.6 ms |

- 达到 P2.1 判据：召回提升、extra ≤ 4%、P95 远低于 500 ms。
- 本轮同时修复了 OSD 的接受语义缺陷（未命中却被当作命中，泄漏未初始化消息），消除了此前 `6H7L W-` 等幻影消息与线程间结果不一致；详见 `docs/04` §4.7。
- 部分 extra 经人工核对为参考集漏收的真实信号，实际误码率低于表中数字。

### 7.5 P2.2 · 逐符号频谱 SNR 回归（2026-10-03）

Android x86_64 模拟器，4 线程，`test/` 60 文件 / 1298 条，`--subtract --depth 3`：

| 指标 | 数值 |
| --- | --- |
| 命中 / 漏解 / extra | 1062 / 236 (18.2%) / 43 (3.3%) |
| 召回率 Recall | 81.8%（与 P2.1 一致，**解码文本不变**） |
| 耗时 | avg **241 ms** / P50 265 ms / **P95 316 ms** / max 335 ms |
| 参考回归（对 WSJT-X txt） | `snr_ref = 0.795·raw + 1.03`，R²=0.506 |

- 满足「不影响解码文本」与「P95 ≤ 500 ms」。
- R²=0.506 未达原定 0.7：7 音调平均（JTDX）与 WSJT-X 参考为不同口径，强信号段 JTDX 比 WSJT-X 系统性低约 8–13 dB，属口径差异而非实现缺陷。
- 性能：SNR 由「每个候选」优化为「去重后每条命中一次」并多线程并行，设备 P95 由 1044 ms → 316 ms。
- 原始输出：`test_results/p2_2_snr_threads4.txt`。
